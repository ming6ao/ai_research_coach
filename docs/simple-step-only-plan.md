# Plan: Simple authoring + step-by-step delivery only

Status: **implemented**. Simple authoring + step-by-step delivery are now the
only modes. See `AGENTS.md` for the current behavior.

Implemented decisions (from §6): per-step `max_score`/`difficulty` kept (with
defaults); task-level `scaffold` editor removed (step scaffolds + composed-stub
fallback); `delivery` column kept as a constant `'phased'` for one release;
legacy partless/block rows normalized by `python -m coach.migrate delivery`;
the "Step k of n" chip is hidden when `phase_total == 1`. The runtime also
tolerates un-migrated rows by keying phased behavior off `parts` (a partless
task is one implicit step).

Goal: collapse the two orthogonal authoring axes into a single mode. Keep the
curator's **Simple** form and the **Step-by-step** (`delivery='phased'`) runtime;
remove **Advanced** authoring and **Single submission** (`delivery='block'`).

This document first explains what the modes are today, then gives a concrete,
file-level plan to reduce the product to the two retained modes.

---

## 1. What the current modes mean

### 1.1 Simple vs Advanced (editor verbosity)

These are **not** behavioral modes — they only gate which form fields the
curator sees. The saved task is identical in either mode.

| Field | Simple | Advanced |
|---|---|---|
| `prompt` (task intro) | yes | yes |
| delivery toggle (Single submission / Step-by-step) | yes | yes |
| task-level `scaffold` | yes | yes |
| `language` | yes | yes |
| `primary` tag | yes | yes |
| steps/parts (key, `prompt`, `max_score`, `difficulty`, primary, scaffold) | yes | yes |
| task-level `difficulty` | no (defaults to 2) | yes |
| task-level `max_score` | no (defaults to 5 / sum of parts) | yes |
| `task_type` | no (defaults to `implement`) | yes |
| task-level `secondary` tags | no (auto-derived from parts) | yes |
| per-part `secondary` tags | no | yes |
| per-part `pass_score` (phased only) | no (defaults to `round(0.7 · max_score)`) | yes |
| `context_notes` | no (auto-generated by LLM) | yes |

Source: `frontend/src/components/Curator/TaskEditor.tsx` (`Mode = 'simple' |
'advanced'`, `const advanced = mode === 'advanced'`). Advanced-only fields are
the `{advanced && ...}` blocks; `mode` is local UI state and is never sent to
the API.

### 1.2 Single submission vs Step-by-step (delivery)

This **is** a behavioral mode, persisted as `tasks.delivery` (`'block'` |
`'phased'`, default `'block'`). It changes scoring, presentation, and session
progress.

| Aspect | Single submission (`block`) | Step-by-step (`phased`) |
|---|---|---|
| What the learner sees | All parts at once | Only the active step, with a "Step k of n" chip |
| Scaffold | Task-level scaffold covering all parts (composed per part if absent) | Each step's own scaffold, else a composed stub; ignored if prior code exists |
| Judge call | Scores every part in one submission | Scores only the active part |
| Belief update | Each part's primary skill + ancestors once, at that part's difficulty; global once on the aggregate fraction | Same, but only the active part per submission |
| Advancement | Task is done after one submission | Step advances when `score ≥ pass_score` (default `round(0.7 · max_score)`) or after `PHASE_MAX_ATTEMPTS` (default 3) failures |
| Code carry-forward | n/a | Prior submission passed back as `previous_code`; editor initializes from it |
| Idempotency | Replays by `task_id` | Replays only an identical answer to the current, unadvanced step |
| Progress state | `session.index` / `asked_task_ids` | `session.task_progress[task_id]` + `phase_attempts[task_id]` + monotonic `submission_index` |
| Session selection | Bank task is consumed on submit | A started-but-unfinished phased task keeps surfacing (`coach/selection.py:_active_phased_task`) until complete |

Key code paths: `coach/config.py` (`DELIVERIES`, `PHASE_PASS_FRACTION`,
`PHASE_MAX_ATTEMPTS`, `default_pass_score`), `coach/session.py`
(`is_phased`, `active_phase`, `task_view`), `backend/v1/sessions.py`
(`submit_answer` branches on `phased`), `coach/shares.py`
(`feedback_from_steps`), `coach/tasks.py` (`validate_parts`, `create_task`,
`update_task`).

### 1.3 How the axes interact

The two axes are independent today:

- Simple + Single submission  → one flat question ("function mode") or a
  multi-part block scored together, low form friction.
- Simple + Step-by-step       → a step sequence authored without advanced
  knobs; pass gate and per-step scaffolds used with defaults.
- Advanced + Step-by-step     → same runtime, full control over
  `pass_score`/secondary tags/context notes.
- Advanced + Single submission → full control, block scoring.

**Target:** one cell only — **Simple + Step-by-step**. A one-step task is the
degenerate case that replaces old flat single questions; a multi-step task
replaces both multi-part blocks and phased tasks.

## 2. Target model

One task shape everywhere:

- `parts` is a **non-empty ordered list of steps**.
- A step is `{key, prompt, tags.primary, max_score, difficulty, scaffold?}`.
- Delivery is **always step-by-step**. `pass_score` is always the default
  `max(1, round(PHASE_PASS_FRACTION · max_score))`; it is not author-editable.
- Task-level `prompt` is a short intro shown above the steps.
- `task_type`, `context_notes`, `tags.secondary`, task-level `difficulty`,
  task-level `max_score` still exist in the data model (the judge, picker, and
  belief system read them) but are **derived/defaulted**, not author-editable.
- The editor has **no mode toggle and no delivery toggle**.
- A single-step task renders "Step 1 of 1"; optionally suppress the chip when
  `phase_total == 1` so it still looks like a plain question.

## 3. What gets removed

### 3.1 Frontend

| File | Change |
|---|---|
| `frontend/src/components/Curator/TaskEditor.tsx` | Delete `Mode`/`mode`, the simple/advanced toggle, and every `{advanced && ...}` block (task `difficulty`, task `max_score`, `task_type`, task `secondary` picker, per-step `secondary`, per-step `pass_score`, `context_notes`). Delete `Delivery`/`delivery` state and the Single-submission/Step-by-step cards; always build `delivery: 'phased'`. Drop the task-level `scaffold` editor (unused by phased `_phase_scaffold`) or keep it only as the single-step scaffold source (decide in §6). Stop sending `task_type`/`difficulty`/`max_score` from the task level; let the backend derive them. Keep step `max_score`/`difficulty` inputs unless we also cut them (§6). |
| `frontend/src/components/Task/TaskPreview.tsx` | No structural change; the `phaseTotal > 1` guard already handles one-step tasks. |
| `frontend/src/components/Chat/ChatView.tsx` | `isPhase` is always true → remove the `isPhase ? 'Next step' : 'Next question'` branch (keep "Retry step" vs "Next step"); `TaskPromptBubble` always gets `phaseIndex`/`phaseTotal`. |
| `frontend/src/api/client.ts` | Drop `delivery` from `Task`, `TaskCreateBody`, and `FeedbackEntry` (or keep as a read-only legacy field but stop writing it). |
| `frontend/src/stores/assessmentStore.ts` | Already phase-aware (`phase_index`/`phase_total`); no behavioral change needed. |
| `frontend/src/components/Curator/CuratorView.tsx` | Check any task summary/delivery badge and drop it. |

### 3.2 Backend

| File | Change |
|---|---|
| `coach/config.py` | Remove `DELIVERIES` (or reduce to a constant); keep `PHASE_PASS_FRACTION`, `PHASE_MAX_ATTEMPTS`, `default_pass_score`. |
| `coach/tasks.py` | Remove the `delivery` parameter, validation, column write, and `update_task` handling; always store `'phased'`. Require/derive non-empty `parts` (wrap a partless task into a single step). Keep `derive_block_tags`, `validate_parts`, `parse_parts`. |
| `coach/session.py` | `is_phased` collapses: treat any task with `parts` as phased (ignore `delivery` for robustness with old rows). `task_view` always emits the phased shape; for partless legacy tasks synthesize a single part. |
| `backend/v1/sessions.py` | `submit_answer`: delete the `else` (block) branch and the block idempotency branch; always take the active-part path. `create_session` `initial_question` path: create a **single-step** task instead of a partless block. |
| `backend/v1/schemas.py` | Drop `delivery` from `TaskCreateRequest` and `TaskPatchRequest`. |
| `backend/v1/tasks.py` | Drop `delivery=req.delivery or "block"`; let `create_task` normalize. |
| `coach/judge.py` | `score_targets` implicit-part fallback can stay as a safety net for legacy rows; once the bank is normalized it becomes unreachable and can be simplified/removed. |
| `coach/shares.py` | `feedback_from_steps` always computes `phase_index`/`phase_total` (drop the `delivery == 'phased'` guard). |
| `coach/selection.py` | Rename `_active_phased_task` → `_active_step_task` (cosmetic) and drop `is_phased` dependence in favor of "has parts and is unfinished". |
| `coach/remediation.py` | `_persist_generated_task` must persist generated follow-ups as single-step phased tasks. |
| `coach/task_decomposer.py` | Ensure `generate_followup_task` returns steps/parts compatible with the single shape. |
| `coach/db.py` | Optional: add `delivery` to `_DROPPED_TASK_COLUMNS` once no code reads it. |

### 3.3 Explicitly retained

- Per-part primary tags → skill/area/domain belief updates.
- `task_type` field and values (default `implement`) — still stored/derived.
- `context_notes` — still auto-generated by `describe_and_categorize`.
- `tags.secondary` — still stored (auto-derived from part primaries) for
  coverage/diversity; just not hand-edited.
- `scaffold` (per step) and `previous_code` carry-forward.
- Pass gate + attempt cap + teaching pause + idempotent replay for steps.

## 4. Data normalization

The runtime can stay correct without a hard migration if `is_phased` keys off
`bool(parts)` and partless tasks are treated as one implicit step. A
normalization migration is still recommended so the bank and old snapshots are
uniform.

New `coach/migrate.py` subcommand (e.g. `python -m coach.migrate delivery`,
dry-run by default, `--apply` backs up first):

1. `delivery='phased'` with parts → no-op.
2. `delivery='block'` with parts → set `delivery='phased'`. Step `pass_score`
   is absent, so it defaults at read time.
3. Partless task → synthesize one step:
   - `key`: `def <name>` parsed from the prompt, else `solution`.
   - `prompt`: the task prompt.
   - `tags`: the task tags.
   - `max_score`: task `max_score` (default 5).
   - `difficulty`: task `difficulty` (default 2).
   - `scaffold`: task `scaffold` if present.
4. Rewrite embedded task snapshots in `active_sessions.session_json`,
   `session_steps.task_snapshot_json`, and `trajectory_shares.snapshot_json`
   the same way so resumed/reviewed sessions match.
5. In-flight block sessions: a block task was already completed in one
   submission, so set `task_progress[task_id] = len(parts)` for tasks already
   present in the session's `asked_task_ids`; leave started-but-unfinished
   phased tasks untouched. If this is messy, document `POST /admin/reset`
   (activity wipe) as the fallback for in-flight sessions.

Because generation paths and `initial_question` must also emit the new shape,
run §5.1 **before** the migration so no new block rows appear mid-rollout.

## 5. Implementation plan

### Phase 1 — Backend unification (no user-visible change yet)

1. `coach/session.py`: make `task_view` always emit the phased shape; add a
   `_single_step(task)` helper that wraps a partless task into one part;
   change `is_phased` to `bool(task.get("parts"))` (or always `True`).
2. `backend/v1/sessions.py`: remove the block branch from `submit_answer` and
   the block idempotency branch; make the `initial_question` path create a
   single-step task.
3. `coach/tasks.py`: force `delivery='phased'` on create/update; forbid a
   phased task with zero parts by synthesizing one; drop `delivery` from the
   public params.
4. `backend/v1/schemas.py` + `backend/v1/tasks.py`: remove `delivery` from the
   request surface.
5. `coach/remediation.py` + `coach/task_decomposer.py`: generated tasks become
   single-step phased tasks.
6. `coach/shares.py`, `coach/selection.py`, `coach/config.py`: collapse the
   `delivery` conditionals; keep `pass_score`/attempt-cap behavior.
7. Run `pytest`; adjust tests per Phase 4.

### Phase 2 — Data normalization

8. Add the `delivery` migration subcommand (§4) with a dry-run report.
9. Run it against a copy / dev DB; verify counts (converted / wrapped /
   skipped). Then run `--apply` with the server stopped.

### Phase 3 — Frontend simplification

10. `TaskEditor.tsx`: remove mode + delivery toggles and all advanced-only
    blocks; always send `delivery: 'phased'`; keep the simple step editor
    (key, prompt, primary, scaffold, and possibly `max_score`/`difficulty`).
11. `ChatView.tsx`: remove the "Next question" branch; always step labels.
12. `api/client.ts`: remove `delivery` from write types; keep phase fields.
13. `CuratorView.tsx`: drop any delivery/mode badge.
14. `cd frontend && npx tsc -b && npm run lint && npm test`.

### Phase 4 — Tests & docs

15. Update / retire tests:
    - `tests/test_phased_tasks.py`: `test_block_delivery_scores_all_parts_in_one_submission`
      becomes a "partless task is a one-step task" test.
    - `tests/test_block_tasks.py`: reframe "block" tests as "step list" tests;
      keep `validate_parts`, `derive_block_tags`, `build_code_stub`,
      `score_targets` coverage (the latter for legacy rows).
    - `tests/test_assessment_flow.py`: block-belief test becomes a
      one-step (or first-step) belief test.
    - `tests/test_curator.py` / `tests/test_tasks_db.py`: drop any delivery
      assertions; add "creating without parts yields one step".
    - Add a migration test under `tests/test_migrate.py`.
16. Docs: update `AGENTS.md` (task types table, curator UI, scoring), this
    file, `docs/phased-tasks-design.md` ("block unchanged" → removed),
    and `docs/data-model.md` (delivery column).

### Phase 5 — Cleanup (optional)

17. If nothing reads `delivery`, add it to `_DROPPED_TASK_COLUMNS` in
    `coach/db.py` and delete the column in a follow-up release. Or keep the
    constant column for one release as a rollback safety net.

## 6. Open decisions (need a call before coding)

1. **Per-step `max_score` / `difficulty`:** keep them in the Simple form (more
   control, current behavior) or hide them and default to 5 / 2 (simplest,
   but flattens adaptive difficulty). Recommendation: keep them — the current
   Simple form already shows them, so removing Advanced doesn't require
   removing them.
2. **Task-level `scaffold`:** the phased runtime ignores it. Recommendation:
   remove the task-level scaffold editor and rely on each step's scaffold;
   when a step has none, keep the composed-stub fallback.
3. **`delivery` column:** drop now or keep as a constant for one release?
   Recommendation: keep for one release, migrate the bank, then drop.
4. **In-flight block sessions:** migrate or reset? Recommendation: migrate
   completed ones; document `POST /admin/reset` for the rest.
5. **"Step 1 of 1" chip:** show always or hide to keep flat questions looking
   flat? Recommendation: hide when `phase_total == 1`.

## 7. Risks

- **Old session snapshots** embed `delivery`/part shapes; the runtime must
  tolerate both. Making `is_phased` key off `parts` (not `delivery`) handles
  this without waiting on the migration.
- **Belief accounting changes** for converted multi-part blocks: previously a
  block updated every part in one submission; as phased it updates per step.
  The total observations are similar but the global update count changes.
  Expect small mastery-number shifts for past candidates upon re-attempt.
- **Idempotency semantics** differ between block replay-by-id and phased
  replay-identical-step. Removing the block branch means a re-submit of an
  already-passed step must be rejected/replayed via the phased path — verify
  `test_failed_phase_replay_is_idempotent` still covers it.
- **Curator muscle memory:** authors lose `pass_score`, secondary tags, and
  context-note overrides. Document the new defaults in the editor's help text
  and in `AGENTS.md`.
- **Generated tasks** currently omit parts; if the generation paths aren't
  updated before the frontend, a generated task would render oddly. Sequence
  Phase 1 first.

---

## 8. Acceptance criteria

- `POST /api/v1/tasks` accepts `{prompt, parts, tags, ...}` and always stores
  `delivery='phased'`; creating without `parts` yields exactly one step.
- A partless legacy task loads and renders as a one-step task with no errors.
- `submit_answer` has a single scoring path: active step only, pass gate,
  carry-forward, idempotent replay.
- `TaskEditor` has no simple/advanced toggle and no delivery toggle; every
  saved task is step-by-step.
- `ChatView` only ever shows "Next step" / "Retry step".
- `python -m coach.migrate delivery` dry-runs, reports conversions, and
  `--apply` normalizes tasks, snapshots, and sessions after a backup.
- `.venv/bin/python -m pytest`, `npx tsc -b`, `npm run lint`, and `npm test`
  all pass.
